# Code Review

Analyze a GitHub pull request, review changed files for material issues, and produce a structured review (local or pending on GitHub).

When the user asks to resolve open PR comments, run **Phase 6**.

---

## Core Workflow

1. Select the PR and review mode
2. Load review references and project conventions
3. Fetch diff + changed files and read full context
4. Analyze findings with severity (Critical / Important / Suggestion)
5. Post review (local chat or GitHub pending review)
6. Optionally resolve open review comments

## Constraints

### MUST DO

- Read full file context before commenting (not only hunk snippets).
- Post all inline comments atomically in one review (never one-by-one).
- Include severity prefix on every inline comment.
- Respond in Portuguese.
- Load and enforce repository-local conventions from the **PR repository** before analysis:
  - `.cursor/**`
  - `.claude/**`
  - `AGENTS.md` and `CLAUDE.md` when present
  - `knowledge/**` when present
- Enforce all rules and good practices explicitly documented in those `.cursor` and `.claude` sources.
- If knowledge convention rules exist in `.cursor/rules` or `.claude/rules`, treat `knowledge/**` as mandatory review context.

### MUST NOT DO

- Do not auto-submit the GitHub review; keep it pending for user confirmation.
- Do not comment on pure formatting/style that linter/formatter already enforces.
- Do not invent issues to fill space.
- Do not post inline comments on lines outside the diff (convert to file-level comment).
- Do not apply this repository's own rules to a different repository under review. Always enforce the target PR repository conventions.

---

## GitHub API Access

Before any GitHub operation:

1. Prefer GitHub MCP if available and authenticated (`get_me`).
2. Fallback to `gh` CLI (`gh auth status`).
3. Resolve `owner/repo` from:

```bash
git remote get-url origin
```

Use the same access method consistently in all phases.

## Phase 1: Select PR

### 1.0 Review mode

Ask:

```yaml
title: "Review Mode"
questions:
  - id: mode
    prompt: "Is this review local-only or should it be submitted to GitHub?"
    options:
      - id: local
        label: "Local only — show the review here in the chat"
      - id: github
        label: "Submit to GitHub — create as a pending review for me to confirm in the web UI"
```

### 1.1 Determine PR

- If user provided PR number/URL, extract and continue.
- Otherwise list open PRs and ask user to pick one.

### 1.2 Fetch PR metadata

Fetch and store:
- `number`
- `title`
- `url`
- `headRefName`
- `baseRefName`
- `headRefOid`
- `changedFiles`, `additions`, `deletions`

Tell the user which PR is being reviewed.

## Phase 2: Load Context

### 2.0 Load repository conventions (mandatory)

Load conventions from the PR repository at `headRefName`.

#### 2.0.1 Always load when present

- `.cursor/rules/**`
- `.claude/rules/**`
- `AGENTS.md`
- `CLAUDE.md`

#### 2.0.2 Knowledge documentation

- If `knowledge/**` exists, load relevant knowledge files.
- If a knowledge rule exists (for example `knowledge-base` guidance in `.cursor/rules` or `.claude/rules`), treat missing knowledge context as an analysis gap and call it out.

#### 2.0.3 Other `.cursor` / `.claude` content

- Enumerate all files under `.cursor/**` and `.claude/**`.
- Prioritize `SKILL.md` files and stack-relevant references.
- Do not blindly load every file; filter by changed paths and stack relevance.
- Skip binaries, lock files, `.skill-meta.json`, and vendored/generated artifacts.
- Deduplicate mirrored Cursor/Claude copies when content is equivalent.

#### 2.0.4 Enforcement rule

Findings must enforce explicit project rules and good practices documented there.
If a project document says `MUST`, `NEVER`, `FORBIDDEN`, or equivalent, violations are normally **Critical**.
If it says conventions/expected behavior (`should`, `prefer`, documented default), violations are normally **Important**.
Optional guidance maps to **Suggestion**.

### 2.1 Get diff

Fetch the PR diff.

### 2.2 Get file-level change details

Fetch changed file entries (`filename`, `status`, `patch`, `changes`).

### 2.3 Read changed files fully

For each non-deleted changed file, read full contents from `headRefName`.
For large PRs, prioritize high-change source files and use `error-recovery.md` rules.

---

## Phase 3: Analyze Changes

1. Load `general-review-rules.md` and apply it to all changed files.
2. Load `pyramid-backend-rules.md` when applicable.
3. Apply project-local conventions loaded in Phase 2.0 with the same authority as built-in rules.
4. Comment only when there is concrete risk, bug, or material simplification.
5. Keep comments direct and actionable in Portuguese.

Before flagging architecture deviations, confirm project patterns from loaded context.

---

## Phase 4: Post Review

### If mode is `local`

- Do not call GitHub APIs.
- Display complete review in chat with:
  - summary
  - findings by severity
  - inline comments grouped by file

### If mode is `github`

- Load and follow `github-review-posting.md`.
- Create one pending review with all inline comments.
- Do not submit the review automatically.

Always mention in the summary:
- Which convention sources were loaded
- Which expected sources were absent

---

## Phase 5: Final Summary to User

### For `github` mode

- Link PR URL
- Inline comment counts by severity
- Remind that review is pending and must be submitted in GitHub UI

### For `local` mode

- Findings count by severity
- Confirm full review was shown in chat

---

## Phase 6: Resolve Review Comments

When asked to resolve comments, load and execute `review-comment-resolution.md`.

---

## Edge Cases and Errors

Use `error-recovery.md` for:
- very large PRs
- permission errors
- rate limits
- stale pending reviews
- non-diff comment targets
